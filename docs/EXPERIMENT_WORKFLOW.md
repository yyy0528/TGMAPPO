# 实验执行与通知规范

适用项目：buoy_network。来源：用户在本聊天提出的长期实验偏好。建立日期：2026-11-12。

本规范约束助手组织实验的流程，不代替训练程序或监控服务。开始、继续、修复或汇报本项目实验前，先读本文件和`docs/TG_MAPPO_EXPERIMENT_PROGRESS.md`，再读取所涉实验目录的manifest、progress与日志。用户当次新指令优先于本文。

## 一、启动前先向用户说明

必须先发简短中文说明，再启动实验，包含：

1. **属于哪部分实验**：基线质量核查、算法对比、消融、收敛速度、WM/PM模块验证、场景泛化、参数敏感性、计算开销或失败案例分析。
2. **本次主要做什么**：要回答的问题、改动点、对照方法，明确哪些是已有结果复用。
3. **规模和设备**：算法/组数、种子数、回合数、每回合时隙、评估频率；模型和仿真分别运行在哪个设备。
4. **预计需要多久**：优先根据同设备、同版本历史实测或短探针估算；没有依据时给粗略范围并说明不确定性，不编造精确数字。计算时间要计入冻结评估与出图。
5. **预计几点结束**：使用北京时间（Asia/Shanghai），写明日期与时间范围，跨天不能只写几点。
6. **监控安排**：说明启动后会检查状态，并在完成或异常时在本聊天通知；尚未成功创建监控时不能说已设置。

推荐模板：

> 本轮属于【实验部分】，主要检查【问题】；只修改【变量】，与【对照】比较。规模为【组数×种子×回合×时隙】，模型【设备】、仿真【设备】。参考【耗时依据】，预计【耗时范围】，北京时间【日期、结束时间范围】完成，包含评估和出图。启动后设置完成/失败监控。

这是告知，不是每次重新索取许可；在用户已授权的范围内继续执行。执行环境要求的审批仍按其规则处理。

## 二、实验执行要求

- 先检查现有任务、运行进程和完成产物，避免重复启动；复用结果前核对版本、配置、模型及报告指纹。
- 沿用原TG-MAPPO与原浮标环境，不把其他研究环境的结果当成原项目结果。模型GPU、仿真CPU为当前分工；实际变化必须告知。
- 每次小步优化、单独验证；相关改动按函数→模块→短训练/保存/冻结评估验证后，再启动长实验。
- 发现bug时先解释哪里出错、原因与影响，再定点修复并重测；没有证据的归因写为假设，配置候选不能写成已证实的bug修复。
- 保留旧模型和原始结果，新实验使用新目录。不得为制造优势而修改测试口径、按种子挑配置或覆盖失败记录。Greedy按用户要求排除后续主队列/主展示，历史结果保留，结论限定于实际比较范围。
- 不把短测、单种子改善或工程通过，写成三种子稳定提升、充分调参或全部论文实验完成。
- 若先前policy不含优化器/RNG，不能将加载权重称为精确续训。

## 三、每轮都设置监控

- 每次新实验启动后，在当前聊天创建或更新与该结果目录绑定的监控；接续同一实验先检查已有监控，避免重复提醒。
- 使用可用的聊天线程定时任务，默认每15分钟只读检查。不能依靠当前回复结束后的普通工具轮询来冒充持续监控。
- 检查manifest、各任务progress、控制器/任务日志、进程与最终report，以及计划中的评估和图表。
- 监控只读，不启动、重复训练，不修改模型或代码。正常运行时保持安静，不因定时触发而发送无意义进度消息。
- 实际速度明显偏离预估或可能超出结束时间范围时，主动说明变化并更新预计剩余时间；用户主动询问时按实际状态回答。
- **完成通知**：本轮计划内的训练、评估、验收及出图均结束后，通知完成项目、关键数值、验收结论、结果/图片位置及尚未完成部分。
- **失败通知**：训练、评估、前缀校验或出图失败，或进程退出但任务未完成，通知具体任务、日志位置、已知原因和下一步；不能把运行中或异常退出写成完成。
- 若候选未达到门槛而未启动后续任务，明确说“未启动/门槛未通过”，不能说长训完成。
- 完成或失败通知后结束对应提醒；继续新一轮时再设置。若监控创建失败，说明失败原因和实际能力，不承诺自动通知。需要本机服务保持运行的监控，应说明依赖条件。

## 四、每轮更新接续记录

在进度文档与该轮说明中记录：实验部分/目的、当前真实状态、源码版本与配置、完整命令、种子和预算、设备、启动时间、预计耗时及结束时间、监控ID与目录、测试结果、完成指标/失败原因、结果链接、下一步。完成阶段性可验收工作后，按已授权的Git保存习惯提交本轮相关文件，保留无关改动。

不要把本文复制进各轮报告。各轮报告只记录本次实际配置、状态、证据和对规范的必要偏离。
